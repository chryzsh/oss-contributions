# oss-contributions — how this repo works

`README.md` is fully generated by `scripts/update_readme.py`. Don't hand-edit
`README.md`, edit the script (or the override dicts inside it) and regenerate.

```
python3 scripts/update_readme.py
```

Runs weekly via `.github/workflows/update.yml` (Monday 06:00 UTC) and on
manual `workflow_dispatch`, using the Action's own `GITHUB_TOKEN`. It only
reads public data (search API, public repo/branch listings), so no extra
secrets are needed.

## The four sections, and how each is derived

### 1. PR table (SCCM / BOF-C2 / AD-BloodHound / Media / Other)

`gh search prs --author=chryzsh --limit 200 --json repository,number,title,state,url,createdAt`,
minus anything where the repo owner is `chryzsh` (those are self-PRs, not
outside contributions). Categorized by keyword match against `owner/repo`
in `CATEGORY_RULES` — first match wins, uncategorized falls into `Other`.

Gotcha: `gh search prs` returns `state` lowercase (`open`/`merged`/`closed`),
and does **not** support a `mergedAt` JSON field (only `closedAt`). The script
upper-cases state on load; don't add `mergedAt` back to the `--json` field
list, it errors out.

To reclassify a repo, add a keyword to `CATEGORY_RULES` (e.g. `configmanbearpig`
had to be added by hand — "ConfigManBearPig" doesn't contain "sccm").

### 2. Original tools

Public, non-fork repos owned by `chryzsh` (`gh repo list chryzsh --json
name,isFork,isPrivate,...`, filtered to `isFork == false`). This pulls in
*everything* non-fork on the profile, including things that aren't really
"tools" — a blog, a personal site, curated "awesome-*" lists, one-off
utilities. Those are named individually in `EXCLUDE_ORIGINAL_TOOLS`; there's
no reliable signal to detect "is this actually a tool" automatically, so new
non-tool repos need to be added to that set by hand when they show up.

Description column is just the repo's GitHub description field. If a repo
shows "—", the real fix is to add a description to the repo on GitHub, not
to hardcode one here.

### 3. Forks extended with own commits

This is the one that took real investigation. The naive approach — "does the
fork's default branch have commits the upstream default branch doesn't" —
is wrong in both directions:

- **False negatives**: fork convention (see `~/share/scripts/CLAUDE.md`) keeps
  `main`/`master` synced to upstream and puts real work on a feature branch.
  `sccm-http-looter` and `go-cmloot` both showed 0 commits ahead on `main`,
  the actual work was on `fix/https-url-regex` and `feat/acl-hunt`. Any
  detection has to check *every* branch on the fork, not just the default one.
- **False positives**: once a PR from a fork branch gets merged upstream
  (especially squash-merged), the fork's branch still compares as N commits
  ahead of upstream forever, because squash-merge rewrites commit hashes —
  the content landed, but the SHAs never will match. `toastnotify-bof`,
  `bofhound`, and `sccmhunter` all showed nonzero `ahead_by` purely from
  this artifact, despite being fully represented already in the PR table.

Fix for both: `find_extended_forks()` in the script:
1. Lists every branch on the fork (`gh api repos/chryzsh/<repo>/branches`,
   **not** `--jq '.[].name'` piped through JSON parsing — that returns plain
   lines, not a JSON array, and silently failed under the shared
   `gh_json_soft` JSON-decode-or-default helper. Use a dedicated
   `branch_names()` that reads the raw output).
2. For each branch, compares it against the *upstream's* default branch via
   `gh api repos/<upstream>/compare/<upstream-default>...chryzsh:<repo>:<branch>`
   and takes the branch with the highest `ahead_by`.
3. Skips the whole fork if its upstream already appears anywhere in the PR
   table (built from the same `gh search prs` results as section 1). That
   PR is the tracked record of that contribution; this section is for work
   that never made it into a PR.

One-line "what changed" per fork is auto-generated from the top 3 commit
subjects on the winning branch (newest first), which is often rough (WIP
notes, "add FORK_NOTES.md", duplicate-looking commits). Write a proper
one-liner in `EXTENDED_FORK_NOTES` (keyed by repo name) once a newly detected
fork's auto-text isn't good enough — this overrides the auto-summary
entirely, it isn't merged with it.

**`EXCLUDE_FORKS`** is for forks that pass the "commits ahead, no PR" test
but still aren't a personal OSS contribution — e.g. `chryzsh/BloodHound` had
30+ branches named `BED-xxxx` (SpecterOps' internal ticket prefix): real
work, but day-job work-in-progress pushed to a public fork, not something to
showcase here. There's no automatic way to tell "day job" from "OSS side
project" apart, so add these by hand as they turn up. If categorization
looks off after a run (a fork that shouldn't be there, or one that's
missing), check here first before assuming the detection logic broke.

### 4. Freshness

`_Last updated` at the bottom is when the script ran, not when any given PR
or fork was last touched. If the weekly Action run failed, this is the
easiest way to notice, an unchanged timestamp for more than \~2 weeks means
check the Action logs.

## If something looks wrong

- **A repo is miscategorized in the PR table** → add/adjust a keyword in
  `CATEGORY_RULES`.
- **A non-tool repo shows up under "Original tools"** → add its name to
  `EXCLUDE_ORIGINAL_TOOLS`.
- **A fork shows up under "Forks extended" that shouldn't be there** (day-job
  work, a reference clone with a stray branch, noise) → add its name to
  `EXCLUDE_FORKS`.
- **A real extended fork is missing** → it either has 0 commits ahead on
  every branch (nothing to show), or its upstream already has a tracked PR
  from you (intentionally excluded, see section 3). Check with the `compare`
  API call by hand before assuming the script is broken.
- **The auto-generated "changes" one-liner is bad** → add an entry to
  `EXTENDED_FORK_NOTES`.
- **Rate limits** — a full run makes roughly 1 call per fork for branches,
  plus 1 compare call per branch on every non-PR-tracked fork (roughly 80-120
  REST calls total as of writing). Comfortably under the Actions
  `GITHUB_TOKEN` default of 1000 req/hour, but if forks/branches grow a lot,
  this is where it'd start to matter.
